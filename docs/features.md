# 功能说明

本文介绍各个可选功能的启用方法和行为细节。部署相关内容见 [部署进阶](deployment.md)。

## 元数据与作品关联

在 `/admin/settings/metadata` 启用需要的在线来源。本地标签和人工修改始终优先，服务不会改写音乐文件。

- **MusicBrainz**：不需要 API Key，但要填写一个有意义的应用标识和联系邮箱（或项目地址）。默认每 2 秒请求一次，低于官方每秒一次的上限，避免连续满速请求触发过载保护；可以用 `MUSIC_SERVER_MB_INTERVAL_MS` 调整。
- **Last.fm 资料**：需要 API Key。在 `/admin/matches` 审核歌手身份；在歌手页可以维护身份、选择简介、上传图片和合并歌手，在 `/admin/merges` 查看或回退合并。
- **Bangumi**：目前 ACG 作品关联使用的在线来源。在 `/admin/work-review` 审核专辑/曲目对应的音乐条目、作品身份和系列建议，在 `/admin/enrichment` 启动或取消任务。VGMdb 增强已经下线，历史数据会保留。
- **作品与系列管理**：在 `/admin/works`、`/admin/series` 管理。本地推断以专辑为主，曲目上明确的标签可以补充单曲关联；在线增强还能单独检索曲目。不同季和剧场版保持为独立作品；不确定或跨媒体的系列关系会进入审核队列，不会被直接合并。人工决定和解除关联的记录在重扫后依然保留。
- **图片与简介**：远程图片下载后从本地缓存提供。简介支持按来源和语言设置优先级，也可以为单个歌手单独选择，人工编辑的文本优先。

如果上游返回 429（或带 `Retry-After` 的 503），当前任务会停止；Bangumi 和 MusicBrainz 还会记录退避窗口。请等一段时间后再重试。

详细的使用规则和已知限制见 [作品关联使用说明](guide/works-association-overview.md) 和 [设计说明](design/works-association.md)。

## Last.fm 播放记录（Scrobble）

1. 在 [Last.fm API 应用申请页](https://www.last.fm/api/account/create) 创建一个应用。
2. 把 API Key 填进 `/admin/settings/metadata` 的 Last.fm 来源卡片，把 Shared Secret 填进 Last.fm Scrobble 卡片，启用并保存。
3. 点击「连接」，到 Last.fm 完成授权，再回到管理页完成连接。不需要公网回调地址；授权 Token 一小时后过期。

满足条件的播放（曲长超过 30 秒、歌手已知）会先写入 SQLite 中持久化的发件箱。网络失败时按退避策略重试，超过 14 天的记录会被丢弃；会话失效后需要重新连接。密钥和会话保存在本地数据库，管理页不会回显。

## AI 打标

在 **管理 → 控制台 → AI 打标** 填写一个 OpenAI 兼容模型服务（Gemini、OpenAI、DeepSeek、通义千问、OpenRouter、本地 Ollama 等）的接口地址、模型和 API Key。大模型会结合声学分析结果、元数据和歌词片段，只从固定词表中为每首歌选择情绪（12 个）和风格（18 个），供每日推荐使用。

- 默认关闭。打开后立即开始首次全量打标，之后新入库或信息有变化的歌曲会自动打标（如果开启了声学分析，会等每首歌分析完成后再打标）。内容没有变化时不会重复调用模型。
- 每首歌大约消耗 2,000–2,700 个输入 token、约 120 个输出 token。按 Flash-Lite 一档的常见报价，1.7 万首大约几美元（以服务商实际价格为准）。页面会显示累计用量和剩余预估，并可以设置每分钟请求数、并发数和思考强度（建议设为 `none`）。
- 可选「复核模型」：当主模型把握较低、无法判断是否为偶像歌曲，或情绪与唤醒度互相矛盾时，交给更强的模型重新打标。「抽样对比」可以先让两个模型各打一批曲目，比较一致程度后再决定是否全量运行。
- 默认会发送歌词片段（每首最多约 600 字，可以关闭）。API Key 和代理地址只能写入、不能读出。访问模型服务需要代理时，在页面上填写（如 `http://192.168.1.2:7890`），或者给容器设置 `HTTP(S)_PROXY`。
- 每首曲目的标签、声学证据和 AI 结果都可以在歌曲的「AI 标签」页查看和人工修正。人工修正优先，重新打标不会覆盖它。

## 每日推荐

每天按情绪和风格生成几个歌单（默认 5 个，每个 25 首；每天 05:00 预生成，第一次打开时也会生成）。生成依据是 AI 打标得到的情绪/风格、声学特征和播放记录：

- **主题**：大约三分之二是情绪或风格（如「治愈温柔」「钢琴」「热血 × 摇滚」），其余是作品漫游、创作者、歌手电台和「好久不见」。根据每个主题的历史评价做 Thompson 抽样，并参考近期偏好。用过的主题冷却 7 天，相邻两天不会用同一种情绪，每周保留一个冷门主题。
- **选曲**：熟悉与探索默认按 70/30 分配；同一歌手最多 3 首、同一专辑最多 2 首；当天各歌单之间不重复；每个歌单 60–120 分钟。按能量起伏排序，开头放熟悉的歌。伤感类曲目默认不进入歌单。
- **标题**：配置了 AI 模型服务时，模型只从服务端算好的候选主题中挑选并起标题（每天大约 1 次请求），不参与选曲；没有配置时使用模板标题。
- **网页入口**：主页左栏顶部显示「今日推荐」（封面拼图、主题、曲数和时长，点击封面直接播放），下方是最近播放。点击标题进入歌单页，可以播放、随机播放、加入队列，标记喜欢或不喜欢（可选原因），「换一个」（每天 3 次），另存为歌单，或者把某首歌设为「不再推荐」。
- **管理 → 每日推荐** 是预览和调试页面，可以查看每首歌的入选原因、候选主题和得分，修改设置或重新生成。App 端的展示将在后续版本加入。
- 声学分析完成后，「相似曲目」也会结合听感（声学 embedding）和元数据。

## 投送到 Sonos / DLNA

部署配置见 [部署进阶 → 投送](deployment.md#投送到-sonos--dlna)。播放栏右侧的投送按钮会列出局域网内的 Sonos 房间（按编组协调器合并）和 DLNA 渲染器。选择设备后，当前播放队列会整体推送过去：

- **Sonos**：通过 AVTransport 把整个队列写入音箱自己的播放队列（`AddMultipleURIsToQueue`，每批 16 首），把传输源切换到 `x-rincon-queue`，从当前曲目和位置开始播放。之后由音箱自己连续播放，关闭网页或 App 都没有影响。播放、暂停、上一首/下一首、进度跳转、循环/随机、音量，以及「下一首播放」「加入队列」、删除和拖动排序，都会同步到音箱队列。页面按 Track 序号和曲目 URI 每秒同步一次状态；刷新页面或从其他客户端打开时，会接管音箱上正在播放的队列。
- **普通 DLNA**：一次只接受一个 URI。队列由服务端保存，每首播完后由服务端推送下一首，同样不依赖客户端在线。
- **音频格式**：Sonos 能直接解码的格式按原文件推送；采样率高于 48 kHz 的无损音频转成 FLAC 48 kHz，服务端会提前在后台生成缓存；Opus 等格式实时转成 MP3 320k。队列 URI 带有媒体 Token，轮换 Token 后需要重新推送。
- **接口**：`GET /api/v1/cast/devices[?refresh=1]`、`GET …/{id}/status`、`GET/POST …/{id}/queue`（`replace`/`append`/`insert`）、`POST …/{id}/queue/remove`、`…/queue/move`、`…/control`（`play`/`pause`/`stop`/`next`/`previous`/`seek`/`playIndex`/`playMode`/`volume`），使用 API Token 或管理员会话鉴权。
