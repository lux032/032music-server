| # | 规则 | 状态 |
|---|---|---|
| R1 | **来源优先级：人工 > Bangumi > 本地规则。** 高优先级的结果覆盖低优先级的，低优先级的结果不能修改高优先级的结果。 | ✅ |

## 2. 关联的数据语义

### 2.1 两个层级

| 层级 | 表 | 含义 | 字段语义 |
|---|---|---|---|
| 曲目级 | `work_tracks` | 这首歌与作品 X 的关系 | `role` 是**权威角色**：op / ed / insert / theme / character / image_song / ost / other |
| 专辑级 | `album_works` | 这张专辑与作品 X 有关 | `role` 只表示**专辑与作品的关系类型**，见 ✅D1 |

### 2.2 ✅D1（选 A） 专辑级关系类型

依照 R4，专辑级不再记歌曲角色，但"这张专辑就是 X 的原声集"是描述**整张发行物**的事实，不属于某一首歌。

- **推荐 A**：专辑级只保留两种值：`ost`（Bangumi 关系为"原声集"，或本地规则识别为 OST）和 `other`（表示"有关"）。原有的 op / ed 等值不再写入专辑级。**原声集专辑不逐首标注 ost**，避免产生大量重复标注。
- B：专辑级一律 `other`，原声集的每首曲目都标 ost。
- 代价：B 在语义上最纯粹，但一张原声集可能有 40 多首曲目，会产生 40 多条曲目关联，作品页的列表也会被撑满。

### 2.3 来源字段

`source` 取值为 `manual` / `bangumi` / `auto`（本地规则），优先级见 R1。

### 2.4 专辑级 Bangumi 角色如何落到曲目上（4.5.1 调整）

从 Bangumi 查到"音乐条目 M 是作品 X 的 片头曲/片尾曲/插入歌/角色歌/主题歌"之后：

1. 专辑与 X 建立专辑级关联（`other`；若关系是"原声集"则记 `ost`）。
2. **在专辑里找标题等于 M 条目名的曲目**：用 strict/loose 口径比较，比较前先去掉版本后缀。命中的曲目建立曲目级关联，角色取 Bangumi 登记的角色。
3. 版本曲目跟随原曲：`track_type` 为 tv_size / instrumental / off_vocal 的曲目，去掉后缀后与原曲同名，就继承原曲的作品和角色。
4. **找不到同名曲目时**（例如专辑条目 "infinite synthesis 6" 下没有叫这个名字的曲目），只建立专辑级关联，不给任何曲目标角色。具体每首歌的角色交给曲目级反查（4.5.4）。

版本后缀的清单与扫描时判断 `track_type` 的规则保持一致（`internal/metadata/reader.go` 的 `InferTrackType`），另外只补充 `-ver.XXXX-` 这类发行版本写法。这属于"文本规范化"，不是推测。

## 3. 各来源的流水线

```
扫描 ──► 本地规则（专辑名 / 显式标签）──► source=auto 的关联
                                              │
Bangumi 任务（scope=all，按以下顺序串行执行）  ▼
  ① 专辑级反查（4.5.1）：专辑 → 音乐条目 → 作品 → 角色 → 专辑级关联 + 按 2.4 落到曲目
  ② 曲目级反查（4.5.4）：曲目 → 单曲条目 → 作品 → 角色 → 曲目级关联
  ③ 作品对齐（已有）：还没绑定 Bangumi 的作品 → 搜索动画/游戏 → 补海报、年份、译名
                                              │
人工（专辑页、作品页、集中审核页）────────────────► source=manual，以及抑制记录
```

### 3.1 冲突处理

| 情况 | 处理 |
|---|---|
| 本地规则推导出 X，Bangumi 也确认 X | 合并为同一部作品（按 external_id、别名、NFKC 标题匹配）；关联的 source 升级为 bangumi |
| 本地规则推导出 X，Bangumi 确认的是 Y（X≠Y） | 见 ✅D2 |
| 本地规则推导出 X，Bangumi 没有结果或进入审核 | 保留 X（R5 兜底） |
| 人工关联了 X | 任何自动来源都不改动；Bangumi 结果只作为候选出现在审核页 |
| 用户解除或拒绝过 X | 所有来源都跳过 X（R3） |
| 同一首歌，曲目级 Bangumi 结果是 X，专辑级已关联 X | 两层都保留，展示时去重（专辑胶囊只显示一次） |

### 3.2 ✅D2（选 A） 本地规则结果与 Bangumi 结果不一致

- **推荐 A**：Bangumi 自动确认 Y 后，移除这张专辑上 source=auto 的 X 关联（不写抑制记录，因为这不是用户意图）；之后重算时，如果专辑已有 bangumi 关联，本地规则就不再给它写专辑级关联。
- B：X 和 Y 都保留，由用户自己清理。
- 代价：A 符合 R1；B 会让本地规则的误判一直留在页面上。

### 3.3 ✅D3（选 A） Bangumi 专辑级反查处理哪些专辑

之前 4.5.1 定的是"只处理没有任何关联的专辑"。现在 R1 规定 Bangumi 优先于本地规则，这个范围需要重新确认。

- **推荐 A**：处理**没有 manual 关联、也没有 bangumi 关联**的专辑，也就是说只有本地规则关联的专辑也会跑，用 Bangumi 校正本地结果。
- B：保持原来的范围，只处理没有任何关联的专辑。
- 代价：A 的请求量会增加（已有本地关联的专辑也要查），但只有这样才能真正体现 R1。

## 5. 集中审核页

- 页面：✅D4、✅D27 把现有 `/admin/enrichment` 的审核区升级为独立页面 `/admin/work-review`（"作品关联审核"），导航入口放在"管理"组"自动增强"旁边，带待审总数角标。`/admin/enrichment` 保留任务列表、"作品关联待审 N 条 → 去审核"入口，以及艺术家关系候选审核区（✅D44：艺术家关系不属于作品关联，不迁移）。歌手身份匹配仍留在原来的"匹配审核"页（那是另一个领域）。
- 分区（Tab，服务端参数 `?tab=albums|tracks|works|series` 实现，不依赖 JS）：
  1. **专辑候选**：专辑封面、候选音乐条目（附 bgm.tv 链接）、得分及依据、关联作品和用途勾选列表；操作为“接受全部 / 只接受勾选作品 / 拒绝并抑制”。
  2. **曲目候选**（4.5.4）：曲名、歌手（查询中直接带出，消除 N+1，D-17）、专辑、候选单曲条目、匹配方式（完全一致 / 去后缀继承 / 多曲名条目 / 仅泛关系）、作品勾选和用途下拉框（D10：修改过用途的关联会记为人工关联）、接受、拒绝。
  3. **作品对齐候选**：现有的 `work_match_candidates`（本地作品 → Bangumi 动画/游戏条目：海报、原名、译名、年份、确认对齐、忽略条目）。
  4. **系列建议**（4.6 批次 6，✅D54）：`work_series_suggestions`（跨媒体与 sequel 建议，见 10.5）：两部作品（海报、标题、类型、年份，链接到作品页）、双向关系标签（自然语言：relationAB 是 A 的关系列表里对 B 的标注，即描述 B，读作“《B》是《A》的<关系>”；两个方向相同时合为“《A》与《B》互为<关系>”；短标签胶囊按 RelationBA ↔ RelationAB 排列，每个词紧挨它所描述的作品）、接受后的效果预览（按当前归属：新建系列（A、B）/ 把 B 加入《X》/ 合并《X》与《Y》）；合并且两方都改过名时提供单选“保留《X》/ 保留《Y》/ 新名字”（D58），只有一方改过名时默认保留该方，两方都是自动名时不显示命名选项；接受/拒绝走 POST（管理员 + CSRF + returnTo），冲突提示“两个系列都改过名，请选择合并后的名字”、失效提示“建议已失效，已移除”、不存在 404，均不返回 500；同一作品出现在多条建议时按作品分组收拢。与作品对齐 Tab 相同：不显示分组切换、不支持 albumId 过滤。
- 通用功能：待审数量角标（每个请求在渲染 chrome 时查询一次，写入布局数据）；右上角"按专辑分组 / 按作品分组"服务端参数切换（`?group=album|work`，分组卡片真实生效；作品对齐 Tab 与专辑无关，始终平铺、不显示分组切换）；支持按专辑过滤（`?albumId=N`，下推到 SQL，过滤状态下 Tab 计数显示过滤后的数量）；接受或拒绝 POST 接口支持站内相对路径 `returnTo`（防开放重定向），处理后回到审核页对应 Tab；拒绝会写入抑制记录（R3）。
- 专辑页和作品页只显示"有 N 条待审核 → 去审核"的入口，不在这两个页面里就地审核。

6. 审核页按第 5 节合并到集中页面（也可以放到 UI 批次再做）。

## 8. 4.5.4 曲目级反查（依据 Oracle 审计 `faddeacd`）

### 8.1 实测结论（api.bgm.tv）

| 曲目 | 结果 |
|---|---|
| legendary future / Leap of faith / 紅蓮華 / only my railgun / 青春コンプレックス | 条目名与曲名完全一致，作品侧登记了唯一具体角色 → **可自动确认** |
| 星座になれたら（专辑收录曲） | 有自己的条目 → 结束バンド 插入歌，**可自动确认** |
| only my railgun -version2020- | 独立条目，且没有关联 → 按条目原名处理，**不能先去掉版本后缀** |
| カタオモイ、c/w 曲目（回回回回回、Dear All…） | 没有同名条目 → 记为未命中 |
| 残響散歌 / 朝が来る、赤い罠/ADAMAS、花の唄 | 只有 `A / B` 这种多曲名条目，Bangumi 的关系登记在整个条目上，**没有指明对应哪一首** → 不能自动确认 |
| Hello、Link | 同名条目很多 → 必须比对歌手 |

请求量：命中一首约 4～6 次，作品级请求全库共享缓存。H1 实测：Bangumi 搜索会把以 `-` 开头的词当成排除条件，`-version2020-` 条目需要先把连字符换成空格才搜得到（缓存键 `music-search:v2:`）。专辑级搜索的请求关键词同样替换连字符，打分仍用原专辑标题。

### 8.2 规则（在 R1～R6 下的具体化）

1. **自动确认的条件**：Bangumi 条目名规范化后等于曲名（strict/loose）+ 歌手一致（本曲 primary 歌手或其别名）+ 登记了具体角色的作品恰好 1 部 + 没有命中任何屏蔽记录。曲目级不打分，只看这几条。
2. **多曲名条目**（`A / B`）：按 ✅D6 处理，不能自动确认。
3. **版本曲目**：先用原曲名查；一个都查不到，并且本地 `track_type` 已经被判定为版本曲目时，才按 `InferTrackType` 的后缀表去掉后缀再查一次（范围见 ✅D7）。`-version2020-` 这类重录后缀一律不去掉。
4. **与专辑级的关系**：曲目级命中与专辑级同一部作品时**仍然写入**曲目级关联，这样角色能精确到具体曲目；展示时去重。
5. **与本地规则的关系**：写入 bangumi 行时删除同一（作品，曲目）的 auto 行；本地标签推导发现已有 manual/bangumi 行时跳过（R1）。
6. **用户意图**（R3）：写入前检查所在专辑的屏蔽记录（`bangumi:<m>`、`bangumi:<m>:<w>`、作品标题 key）、专辑候选里是否已拒绝，以及本曲目的屏蔽记录；`RemoveWorkTrack` / `DeleteWork` 对 bangumi 行也写入屏蔽记录。
7. **数据**：migration 027 只新建 `track_subject_candidates` 和 `track_enrichment_misses`，不重建 `work_tracks`（026 已放开 bangumi 来源）。track_id 在专辑合并和重新扫描时都不变，所以相关记录会自动跟着走。
8. **代码复用**：搜索、条目名比对、歌手拆词、反查作品和角色、作品落地，与 4.5.1 共用同一套实现。
9. **调度**：`all` 的执行顺序为 专辑级 → 曲目级 → 作品补资料；专辑页的「从 Bangumi 查找」会同时执行专辑级和曲目级。专辑级任务完成后还会顺带刷新该专辑已关联作品的资料，使专辑页一键补齐。

### 8.3 与第 2 节的关系

Oracle 指出，`TracksForWork` 会把专辑级角色摊给整张专辑的所有曲目，导致 c/w 在作品页上也显示成 OP。按 D1-A，专辑级只写 `ost` / `other`，这个问题会随之消失：摊到曲目上的只会是 "其他" 或 "OST"，真正的 OP 只来自曲目级。展示上的细节放在 UI 批次（4.5.5 / 4.5.6）处理。

### 8.4 实施拆分（排在 4.5.1 提交之后）

S1 存储层（migration 027、屏蔽和去重、共用落地函数）→ S2 匹配（共用函数抽取、曲目级规则，测试数据用本次实测的真实 JSON）→ S3 调度 → S4 审核页和接口 → S5 reviewer 门禁 + 本地库副本试跑。

- **H1（类型纠正导致重复作品）**：已绑定 Bangumi 的作品按 Bangumi 大类复用；anime/movie 互相兼容，未绑定作品仍严格按类型解析，避免纠正为 movie 后本地 TV 标题新建同名 anime。

## 10. 系列（4.5.3 / 4.6）

### 10.1 数据模型（migration 029）

| 表 | 含义 |
|---|---|
| `work_series` | 单层系列（D24）：`title`、`title_source`（auto/manual）、`representative_work_id`（作品删除时 SET NULL） |
| `work_series_members` | 成员，`work_id` 为主键（一部作品最多属于一个系列），`source` 为 auto/manual；作品或系列删除时级联 |
| `work_series_locks` | 用户拆出过的作品，自动归组永久跳过（R3）；手动加入系列时解除 |

### 10.2 归组规则

1. 只对绑定了 Bangumi **type 2** 条目的作品归组（R2），不加任何本地推测（不按标题前缀、年份相近判断同系列）。
2. 从 `/v0/subjects/{id}/subjects` 取关系，只沿 **续集 / 前传** 走（D21）；总集篇、全集、番外篇、衍生、不同世界观、主线故事等一律不走。关系按无向图做 BFS 求连通分量。
3. 库外条目可以搭桥（D23）：离开库内作品不超过 **3 跳**，每个分量最多 **40 个节点**（达到上限时同时停止出队和追加）；BFS 以 (subject, 最小库外跳数) 为状态、发现更小的跳数时重新入队，保证结果与遍历顺序无关；visited 集合保证有环时终止。只把库内作品写成成员，不记录库外条目。
4. 请求失败的分量本轮跳过，已有归属不变（熔断：连续 5 次失败中止阶段）；增量重跑时自愈。404 视为无关系。
5. 存储层 `ApplyAutoSeries` 在一个事务内完成：只改 source=auto 的成员；候选同时排除锁定作品和任意系列中的 manual 成员（P3：manual 成员等同于锁定，不参与自动归组，也不会被自动流程挪动或删除）；写入分两段执行——先对所有系列做删除、再统一插入，保证一部作品跨系列移动时不违反 `work_id` 主键；已有系列按全局贪心跳匹配（所有（分量，系列）候选对按交集降序 → 分量大者优先 → title_source='manual' 的系列优先 → 系列 id 小者优先依次认领，每个系列只被一个分量认领，D41），保住用户改过的系列名；分量与两个及以上改名系列有交集时不自动合并，本轮跳过（D41-A1；冲突解决后，改名系列的名字最终落在哪个系列上，可能与历史处理顺序有关，不会丢数据，只是结果依赖顺序）；分量不足 2 个候选时不建系列；auto 成员 ≤1 且没有 manual 成员的系列删除。本轮没有处理到的 auto 成员（请求失败、熔断或被跳过的分量）一律保留，不会因部分失败被拆掉。
6. 代表作品与系列名（D25）：按成员的作品年份 → Bangumi 播出日期 → 作品 id 取最早者为代表；`title_source='auto'` 时系列名跟随代表作品标题，`title_source='manual'` 时只更新代表作品不动名字。重复运行是幂等的：结果不变，不刷新 `updated_at`；成员变动通过 `enrichment_provenance`（field `series`，source `bangumi`）记录。

### 10.3 用户操作语义（R3）

| 操作 | 效果 |
|---|---|
| 从系列中拆出 | 删除成员并写入 `work_series_locks`，自动流程不再加回；拆出后系列只剩 ≤1 个 auto 成员且无 manual 成员时同时解散 |
| 手动加入系列 | `source='manual'`，解除该作品的锁定，并从原系列移出（一个作品只属于一个系列） |
| 重命名系列 | `title_source='manual'`，自动流程不再改这个名字，但仍会更新代表作品 |
| 解散系列 | 全体成员写入锁定并删除系列；自动流程不会重建（全锁定的分量不会建系列）。选择锁定而不是“用户解散”标记（D39），因为锁定是现成的单作品意图机制，不需要额外状态。**已知副作用**：以后新入库两部以上同一续集链的作品时，它们可能单独组成一个只有新作品的系列，用户可以手动处理 |
| 删除作品 | 成员级联删除；被删的是代表作品时重算；空系列或只剩 1 个成员的 auto 系列一并清理（含 `CleanupAutoWorks`） |

### 10.4 调度与展示

- 系列阶段放在作品对齐阶段之后，属于 `all` 和 `works` 范围，复用 `subject-rel:<id>` 缓存键、cachedJSON、runMemo、节流、取消与熔断。
- `/works` 列表把同一系列折叠为一行（系列名 + “共 N 部”，可展开成员链接）；分页与总数按折叠后的行数计算，首字母索引与排序都按显示的系列名。
- 作品详情页显示所属系列与同系列作品（链接），提供拆出、重命名、加入、解散表单（管理员 + CSRF）；解散按钮旁注明“解散后这些作品将不再参与自动归组”。完整系列管理页与跨媒体建议留待 Phase 4.6 后续批次。
- 剧场总集编之类的条目不会通过 总集篇 关系进组；但若它们彼此之间登记了 续集/前传（如 ぼっち・ざ・ろっく！ 的两部剧场总集编），按 R2 它们会单独组成自己的系列。

### 10.5 跨媒体与 sequel 建议（4.6 批次 5，migration 031）

- 自动归组仍然只沿续集/前传、只覆盖 type 2 条目（D21）。其余关系一律不自动进组，而是生成**建议**进集中审核（R6）：`work_series_suggestions` 一行是作品对作品（D53），记两个方向的 relation 文本与 kind（cross/sequel）。
- 配对只在两端都在库内、且这一轮都成功拉到关系时进行；必须双向核对：A→B 与 B→A 的 relation 要组成 D52 的白名单关系对（cross），或互为续集/前传且满足 D67 收窄条件（sequel：至少一端是系列 manual 成员，或两端都是 type 4）。配对核心是纯函数 `seriesSuggestionPairs`（internal/enrichment/series_bangumi.go）。
- 跳过：两部作品已在同一系列；任一方被锁定（D56）；这对 subject 已被接受或拒绝过（D55，`work_series_suggestion_decisions` 按 subject 对永久记忆）。锁定、决定与同系列检查在落库事务里再核对一次（INSERT … SELECT … WHERE NOT EXISTS），生成期的竞态不会把建议写回来；任一端被锁定的旧建议在下一次落库时删除，被锁定的作品产生的建议在 Pending 查询里也会被过滤，接受时重读发现锁定则返回 ErrSeriesSuggestionStale 并删除建议（不清锁）。换绑到非 type 2/4 条目、或 subject 被多个作品绑定的作品，只要本轮解析没有失败就算已处理，其残留旧建议会被删除。
- 生成时机：enrichBangumiSeries 的 BFS 与 ApplyAutoSeries 完成且未中止时执行；type 2 的关系复用 BFS 的 runMemo 与 `subject-rel:<id>` 缓存（不产生额外请求），type 4 按需拉取（同样走 cachedJSON、节流、取消与熔断）。建议用单独的 suggestLibrary（含 type 4），**不改 BFS 的 type-2 library**，游戏不会被续集链拉进自动归组。落库在一个事务里 upsert；两端本轮都成功、但没再产生的旧建议删除；拉取失败的作品的旧建议保持不动。
- 接受（AcceptSeriesSuggestion）按两部作品当时的归属：都不在系列里 → CreateWorkSeries；只有一方在 → AddWorkToSeries（manual）；分属两个系列 → MergeWorkSeries（名字按 D58，两方都改过名又没给名字时返回 ErrSeriesTitleConflict）；已在同一系列 → 直接关闭。拒绝只记决定。两者都删除建议行。
- 计数并入 PendingWorkReviewCounts / 导航角标（与列表同口径：任一端被锁定的建议不计入）；审核 Tab（/admin/work-review?tab=series）与系列管理页 UI 已在批次 6 上线（见第 5、6 节）。
- 实测备注：薬屋のひとりごと 剧场版（599894）在 Bangumi 上登记的是“衍生”（TV 侧 420628 登记衍生、剧场版侧登记主线故事），不会自动进组，只能通过建议进入系列。

### 10.6 人工合并与新建（4.6 批次 5 数据层）

- `MergeWorkSeries(keep, drop, title)`：drop 的全部成员移到 keep 并一律改为 manual、清除它们的锁（D57），删除 drop；名字按 D58；移动写 provenance（field `series`，source `manual`，含 mergedFrom）。keep==drop 或任一方不存在都是错误。
- `CreateWorkSeries(title, workIDs)`（D61）：成员一律 manual 并清锁；成员原在别的系列时先移出，原系列做退化清理或刷新代表作；名字可空（auto，跟随代表作）。
- `ListSeriesPage(q, limit, offset)`：管理页数据源，返回成员数与类型分布（GROUP BY w.type），支持按系列名或成员名搜索并返回总数。
- 批次 6 已上线管理页 UI（见第 6 节）：POST /admin/series（新建，名字可选、至少一部作品）、/admin/series/{id}/members（加入或移入）、/admin/series/{id}/members/{workId}/remove（移出）、/admin/series/{id}/merge（dropId + 命名单选）；改名与解散复用作品页既有路由并支持 returnTo。

### 10.7 B1 修正（D59）与 D66 口径说明

ApplyAutoSeries 原先按“全部成员”计算分量与系列的重合度：用户手动加入足够多的作品后，由这些 manual 成员组成的分量会把系列从真正的 auto 分量手里“认领”走。修正后重合度只计算未锁定的 auto 成员（manual 成员是钉在系列上的用户意图，见 P3），D41 的冲突检测用同一口径。回归测试：TestApplyAutoSeriesManualAdditionsDoNotStealSeries。

保持该口径的两个已知行为（D66）：

1. **manual-only 系列不会被 auto 分量认领**：同一轮从同一续集链进来 ≥2 部新季时，新季会另建一个 auto 系列，链暂时分成两个系列；靠 sequel 建议（D67a）提示用户，人工合并（MergeWorkSeries）修复。
2. **只凭 manual 成员与改名系列重合不再触发 D41 冻结**：D41 冻结保护的是“auto 归属被两个改名系列争抢”的冲突；manual 成员不构成归属争抢，因此不再冻结（分叉 3）。固定行为的测试：TestSeriesManualOnlySeriesNotStolenAndSequelSuggested。
